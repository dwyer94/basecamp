# 06 · Decisions and open questions

## Decisions

| ID | Decision | Date | Why |
|---|---|---|---|

| D-02 | Several servers can run at once, each with its own start-on-boot toggle | 2026-10-26 | Owner's pick |
| D-03 | Two roles: admin (full) and friend (read-only view) | 2026-10-26 | Owner's pick |
| D-04 | v1 extras: crash auto-restart, save backups, Discord webhook. Scheduled updates are Later | 2026-10-26 | Owner's pick |
| D-05 | Live console with commands (stdin or RCON) | 2026-10-26 | Owner's pick |
| D-06 | Python 3.13 + FastAPI + SQLite, plain HTML/JS UI | 2026-10-26 | Matches owner's other projects; no build step |
| D-07 | Run as a scheduled task at startup, own Python copy, own folders | 2026-10-26 | Starts before login; own runtime keeps it apart from other apps' firewall rules |
| D-08 | Bind to `127.0.0.1:8150`; reach it via `tailscale serve` (Plan A), fallback Plan B | 2026-10-26 | Loopback-only fits the rules; HTTPS for the copy button; identity without passwords |
| D-09 | Game servers outlive Basecamp restarts and are reattached, console included (via their host process, D-25). Only if a host itself dies is the game adopted bare, without console until restarted | 2026-10-26 | Updating Basecamp shouldn't kick friends off |
| D-11 | Runs as the owner's own account (not elevated, task set to "Do not store password"), no dedicated Windows user. Game installs, saves and SteamCMD stay where they are | 2026-10-26 | Nothing is on the public internet, so a separate user is extra hassle (moving saves, permissions) for little gain. Revisit if servers go public (playit.gg etc.) |
| D-12 | Basecamp updates itself from GitHub Releases via a small launcher that swaps version folders and rolls back if the new one isn't healthy | 2026-10-26 | Owner's idea; no manual copying to the prod PC |
| D-13 | Releases are built and signed (Ed25519) on the dev PC, not in GitHub Actions; Basecamp only installs signed zips | 2026-10-26 | Basecamp runs what it downloads; the key never leaves the dev PC, so a GitHub account breach can't push code to the prod PC |
| D-14 | Self-update installs on the admin's tap by default; auto-install at a set hour is an option | 2026-10-26 | Updates drop the live console of running servers until they restart, so you choose when |
| D-15 | **Public** GitHub repo. Release checks need no token | 2026-10-26 | Nothing sensitive in the code; simpler setup. Secrets, the data folder and the signing key never go in the repo |
| D-10 | Friend access: research only for now; recommend trying Tailscale device sharing first | 2026-10-26 | See [03-friend-access.md](03-friend-access.md) |
| D-16 | Supervisor uses threads (a watcher and an output pump per running server), not asyncio | 2026-10-26 | Blocking Windows process calls are simpler on threads; the Phase 2 API calls in from worker threads and gets state changes from `Supervisor.add_listener` |
| D-17 | Ctrl+Break is raised by attaching to the game's hidden console, not by `os.kill(pid, CTRL_BREAK_EVENT)`: normally by the server's host (D-25), which has no console of its own; the `basecamp/winctrl.py` helper process is the fallback for bare adopted games | 2026-10-26 | `CREATE_NO_WINDOW` gives each game its own hidden console, and Windows only delivers console events to the sender's own console. Basecamp under `pythonw.exe` has no console at all. The helper also works for adopted servers |
| D-18 | Stop recipe = ordered steps (`stdin`, `rcon`, `ctrl_break`), each "do it, then wait up to N s for the exit"; kill always follows. A step that can't be done (no stdin after adoption, RCON not wired yet) is skipped without waiting. No recipe = Ctrl+Break, 30 s, kill (R-22) | 2026-10-26 | Covers the R-22 example ("save, wait 10 s, quit, wait 60 s, Ctrl+Break, kill") and degrades sensibly for adopted servers |
| D-19 | Duplicate ports are refused at **start**, not when saving a server: a port is busy if another active Basecamp server lists it (even before that game has bound it) or the OS says it's bound (exclusive bind test plus the netstat table) | 2026-10-26 | Two configs of the same game on one port are fine as long as only one runs |
| D-20 | Phase 1: an unexpected exit ends in **Crashed**; auto-restart (R-05) comes in Phase 4 on top of the state listener | 2026-10-26 | Keeps the crash policy in one place, built with the Discord notifier |
| D-21 | Hosts (D-25) and the games they start are started with `CREATE_BREAKAWAY_FROM_JOB` when the job allows it, else without | 2026-10-26 | Task Scheduler runs tasks in a job object; breaking away keeps games alive if the Basecamp task is stopped (D-09). Check on the prod PC in Phase 0 (Q-10) |
| D-22 | Launcher games: the template's real exe name is looked for among the launcher's descendants (by parent PID scan, which still works after the launcher exits) for up to 60 s; until then the launcher is tracked. The host does this (ctypes Toolhelp snapshot), so it works while Basecamp is down | 2026-10-26 | Palworld-style launchers exit soon after starting the real server |
| D-23 | No `CHECK` constraints on enum-like columns; the pydantic models validate them. RCON passwords are not in the DB (they go in `secrets.toml`) | 2026-10-26 | A new enum value would otherwise need a table rebuild, which add-only migrations forbid. Secrets rule (R-82) |
| D-24 | Dev PC venv uses CPython 3.13 fetched by `uv` (the PC only has 3.14 installed) | 2026-10-26 | Matches the release target (`--python-version 3.13`, docs/07) |
| D-25 | **One host process per running server** (`basecamp/host.py`, standard library only). Basecamp starts it detached and outside its job; the host starts the game, owns its pipes, writes the console log, keeps a replay buffer, and serves a control channel on `127.0.0.1` (ephemeral port, per-run random token stored in the data folder). It exits only after its game, leaving `exit.json`. Basecamp reattaches via `state.json` (host PID + exe + create time, port, token); an exit while Basecamp was down is reported on reattach as Crashed unless the stop was asked for. Host gone but game alive: adopt the bare game as before | 2026-10-26 | Owner's call (R-04a): a game must never depend on Basecamp's pipes, and the console must survive Basecamp restarts and self-updates. TCP loopback over a named pipe: simpler with the standard library, and binding to `127.0.0.1` needs no firewall rule |
| D-26 | Host compatibility: the hello negotiates `min(Basecamp's protocol, host's protocol)`. Protocol changes are additive only (new ops or fields, never removed or changed); each side keeps speaking every older version; a client only uses ops in the negotiated version. A Basecamp that meets a host below its `MIN_HOST_PROTOCOL` treats the game as bare. Hosts run from a copy in `<data>\hosts\bin\` named by content hash, never from a version folder | 2026-10-26 | A host lives as long as its game, so it can be several Basecamp releases old, or newer after a rollback. The launcher prunes old version folders (docs/07) |
| D-27 | **Plan A confirmed** for auth: Basecamp binds to `127.0.0.1:8150`, `tailscale serve` publishes it over HTTPS, admin = owner's `Tailscale-User-Login` (or localhost), everyone else = friend view. Plan B (password) not built | 2026-10-26 | Q-02 test from the owner's phone and both PCs: login header present, page secure, clipboard copy works |
| D-28 | Who is admin (Plan A details). The `Tailscale-User-Login` header counts only when the TCP peer is loopback (Uvicorn's `proxy_headers` is off, so the peer is the real socket). Login in `admin_logins` (data-folder `settings.toml`, case-insensitive) = admin; any other login = friend. **Local admin** = loopback peer, a loopback `Host`, and no Tailscale or `X-Forwarded-*`/`Forwarded` header. Anything else from loopback (Serve traffic without a login: tagged devices, Funnel, another proxy) = friend. Spoofing is accepted from the PC itself: any local process can set the header, but it could equally send none and be the local admin, so it gains nothing | 2026-10-26 | Serve strips client-sent identity headers and connects from loopback, so the header is trustworthy only from there. Serve sends no login for tagged devices, so "loopback with no login" alone would have made every tagged device admin. Checked against Serve's documented behaviour; Q-11 confirms the forwarding headers on the prod PC |
| D-29 | Browser guards for the local admin: requests whose `Host` isn't a loopback name or `*.ts.net` get 400 (DNS rebinding), and POST/PUT/DELETE and WebSockets with an `Origin` other than the page's own get 403 | 2026-10-26 | A web page open in a browser on the prod PC could otherwise drive Basecamp as the local admin (cross-site POST, or a WebSocket, which CORS doesn't cover). Requests without `Origin` (curl, scripts) are local anyway |
| D-30 | The friend view is built from an allow-list (`FRIEND_FIELDS`: id, name, state, uptime, join address), never by trimming the admin view; the status WebSocket uses the same function. Tests check the friend JSON's keys exactly | 2026-10-26 | R-71, R-82: a field added to the admin view later can't leak to friends |
| D-31 | Templates load from the repo's `templates\` **and** `<data>\templates\`; a data-folder template with the same id overrides the built-in one, and the UI shows each one's source. Templates are validated strictly (unknown fields refused, file name = id); a bad file is skipped and listed with the reason. Fields not checked against a real install are listed in `unverified` and shown in the UI. A template only pre-fills the form; the server remembers its `template_id` | 2026-10-26 | Owner's request: add or fix a game without waiting for a release. Strict validation turns a typo into a message instead of a silently missing setting. Guide: [08-templates.md](08-templates.md) |
| D-32 | Start answers when the host is up (so port-in-use errors show at once). Stop, restart and kill answer 202 at once and run on their own thread; the page follows the status WebSocket (pushed on every state change, refreshed every 5 s for uptime, CPU and RAM) and the console | 2026-10-26 | A graceful stop can take minutes; an HTTP request shouldn't hang that long |
| D-33 | The join host (`join_host`) and the admin logins (`admin_logins`) are settings in the data folder's `settings.toml`, with no default in the code. Until `join_host` is set, the page says so instead of showing an address | 2026-10-26 | The repo is public: the tailnet IP and logins must never be code defaults. A Settings page comes in Phase 5 |
| D-34 | No front-end library: plain JS with a small `el()` helper, no vendored files | 2026-10-26 | Two pages and a form didn't need htmx or Alpine; nothing to keep updated |
| D-35 | Backups are the zip files themselves, with no index in the DB: `backups\<id>\YYYYMMDD-HHMMSS-<reason>.zip`, plus a JSON zip comment (server, save folder, file count). Each one is written to `.tmp` and renamed when complete, and fails as a whole if any file can't be read | 2026-10-27 | Nothing to keep in step: a zip copied in or deleted by hand shows up as it is. A half backup that looks whole is worse than none |
| D-36 | Scheduled backups run only while a server is Running, every `backup_every_h` counted from its newest backup or last failed try (so a failure posts once per interval, not every minute). Retention keeps the newest `backup_keep` of all kinds (manual, scheduled, pre-restore, later pre-update). Restore needs the server Stopped or Crashed and holds its action lock throughout (`Supervisor.hold`). It makes a `pre-restore` backup, unpacks into a new folder next to the save folder, then swaps the two. Zip entries that would land outside are refused | 2026-10-27 | A stopped server's save doesn't change. The safety backup makes every restore undoable, and the swap leaves the old save untouched if unpacking fails |
| D-37 | Webhook URLs live in `secrets.toml`: one main URL plus an optional one per server that replaces it, so both answers to Q-07 work. The page only takes `https://discord.com/api/webhooks/...` URLs, shows them masked, and never puts them in the audit log or logs. Basecamp rewrites `secrets.toml` when you save one (other keys are kept, comments are not) | 2026-10-27 | A webhook URL is a posting credential. The repo is public, so it never goes in the repo, settings.toml or the DB |
| D-38 | Discord messages go on a queue with one worker thread: retries after 5, 30 and 120 s, 429 waits honoured, other 4xx answers (a deleted webhook) not retried, `@everyone` and other mentions turned off. Events: up (Starting to Running only, so a reattach posts nothing), stopped, crashed, gave up, backup failed, update (Phase 3), plus "Basecamp started after the PC restarted" once per boot (`boot.json`). Per server, the DB stores the events turned **off** (`notify_off`), so events added later start on | 2026-10-27 | R-62: Discord being down never blocks a start, stop or backup |
| D-39 | Crash restart (R-05) is a supervisor listener (`crashes.py`). A crash restarts after 10 s; the 3rd crash in 10 minutes leaves it Crashed and clears the count, so pressing Start gives it its retries back. A restart that fails to start counts as giving up. Stop, Kill and Delete cancel a pending restart; a manual Start during the wait wins. Runs that crashed while Basecamp was down are restarted too. The delay, limit and window are settings | 2026-10-27 | Keeps the supervisor's state machine unchanged (D-20). Giving up after a failed start avoids a loop that can't succeed by itself |
| D-40 | Phase 4 (backups, crash restart, Discord) was built before Phase 3 (SteamCMD) | 2026-10-27 | Owner's call: the update flow starts with a backup. Phase 3 calls `Backups.make(server, "pre-update")` and posts the `update` event |
| D-41 | An install or update holds the server's action lock from its turn in the queue to the end (`Supervisor.updating`). It stops the server through the supervisor's own stop path and recipe, and that stop ends in **Updating**, not Stopped, so Discord gets no "stopped" message. While it runs, Start, Stop, Restart and Restore answer 409 instead of waiting for the lock; Kill still works. A queued run doesn't block anything: the server runs as normal until its turn | 2026-10-27 | R-04a: no second way to stop a game. A request waiting up to an hour for the lock would look hung, and a stop that waited would stop the freshly updated server |
| D-42 | The pre-update backup comes first, while the server still runs. If the server has no save folder set, or the folder doesn't exist yet, the update goes on with a console note. If the backup fails (a file can't be read), the update stops there with nothing changed and the server still running | 2026-10-27 | R-51 asks for a backup before every update; a failing one must not be skipped silently. A server with nothing to back up shouldn't be impossible to update |
| D-43 | Each install or update is a row in `steam_runs` (who, result, builds before and after, backup name) plus a log file. A failed run (or one interrupted by a Basecamp restart) marks the server until a later run succeeds. Start still works after a failure, behind a confirm. The queue itself isn't kept across restarts: runs left queued or running are marked interrupted | 2026-10-27 | R-32: the mark and the output must outlive the page and a Basecamp restart. The owner may know the files are fine, so the mark warns rather than locks. Resuming a half-done update by itself after a restart is riskier than asking again |
| D-44 | Success needs exit code 0 **and** SteamCMD's "Success! App ..." line. Exit code 7 or "Update complete, launching Steamcmd" without that line is SteamCMD updating itself: run once more. Timeout per run, 60 min by default; on timeout or cancel the process tree is killed. A cancel before SteamCMD starts changes nothing (the server is started again if it was running); a cancel during SteamCMD counts as a failure | 2026-10-27 | SteamCMD's exit codes alone aren't reliable. Half-written game files are the risk R-32 is about, so a killed run is treated like a failed one |
| D-45 | SteamCMD's output goes into the server's own console (a `steam` line source), and the phase and download percent into the server's admin view on the status WebSocket (at most once a second) | 2026-10-27 | Reuses the console WebSocket and console.log instead of a second stream; the page already follows both |
| D-46 | First install (R-11) only for a stopped server whose install folder is missing or empty. No backup, and it isn't started afterwards. Update needs the folder to exist | 2026-10-27 | Never write SteamCMD output over files it didn't put there. A fresh install usually needs its config checked before the first start |
| D-47 | The SteamCMD path is `steamcmd_path` in the data folder's `settings.toml` (default `%USERPROFILE%\Desktop\SteamCmd\steamcmd.exe`); the page says when it isn't found. A path ending in `.py` runs with Python, so the dev PC and tests use `tools/fake_steamcmd.py` | 2026-10-27 | Settings live in `settings.toml` until the Phase 5 settings page (D-33). The fake shows progress, success, failure, self-update and a hang without downloading anything |

| D-48 | The page names a config file by its place on the server's `config_files` list (`/configs/{n}`), never by a path. Every read, save and restore still runs the guard: the path is resolved (`..`, symlinks, junctions, case) and must be the same file as a list entry. Refused: a list entry that is a folder, a file that is itself a link, paths with streams (`file:stream`) or device prefixes (`\\?\`, `\\.\`), anything inside Basecamp's data folder (secrets.toml), and a relative entry when the server has no install folder. A refused request is audited | 2026-10-27 | R-43. Index addressing gives the page nothing to traverse with; resolving again on each request catches a file swapped for a link after it was listed. The data-folder rule stops the editor being a way round the masked webhook |
| D-49 | Files keep their shape: the encoding (UTF-8 with or without a BOM, UTF-16 LE/BE, else Windows-1252) and line endings (CRLF unless the file is mostly LF; a new file gets CRLF) are detected on read and used on save, so an unchanged file saves byte for byte the same. The page only sees `\n`. A character the file's code page can't hold is refused, not replaced. Files over 2 MB aren't opened | 2026-10-27 | Games write UTF-16 and BOMs and some refuse a file whose encoding changed. Silent replacement would corrupt a setting |
| D-50 | Before each save or restore the old file is copied byte for byte to `<data>\config-history\<server id>\<file name>-<hash>\YYYYMMDD-HHMMSS-ffffff-<save or restore>.<ext>`; the newest `config_copies_keep` (20) are kept per file. Restore puts a copy back byte for byte, after copying the current file the same way, so a restore can be undone. A save sends the hash of the file as the page loaded it; if the game rewrote the file meanwhile, the save is refused (409) until the admin chooses to overwrite. JSON is parsed before saving (refused with line and column); other formats are saved as typed. Writes go to a temp file in the same folder, then replace the original | 2026-10-27 | R-41. Folder per file path, so reordering the list doesn't mix histories. Several games (Enshrouded, Palworld) rewrite their config on exit; silently overwriting that, or being overwritten, would lose changes |
| D-51 | After a save or restore the answer says whether the server is running, and the page offers **Restart now**, which is the normal restart route (stop recipe, then start). The editor keeps Palworld's one-line `OptionSettings=(...)` intact (no wrapping in the file; a "wrap long lines" view option) and can also show that line as one field per setting, rebuilt in the same order and quoting | 2026-10-27 | R-42 and R-04a: no second way to stop a game. Editing a 6 KB line on a phone is impractical; fields make the done-when check workable |
| D-52 | The Settings page edits `join_host`, `steamcmd_path` and the backup defaults for new servers (`default_backup_every_h`, `default_backup_keep`, optionally applied to every existing server). They are written to `settings.toml` line by line (comments and other keys kept; the result is re-parsed before it replaces the file) and applied at once to the one shared Settings object. Admin logins and the other settings stay a `settings.toml` edit plus a restart, and the page shows them read-only. The Discord webhook moved onto this page: one main webhook (Q-07), per-server webhooks under "Advanced". The audit log records which settings changed, not their values | 2026-10-27 | D-33 promised a settings page. Admin logins from the page could lock the owner out from the phone (localhost would still work, but that means being at the PC). Values the page changes are read where they're used, so applying them live needs no restart |
| D-53 | A release is `basecamp-<v>.zip` plus `basecamp-<v>.zip.sig`, the raw 64-byte Ed25519 signature of the whole zip. Inside, `manifest.json` gives the version, `min_launcher`, `python` (`3.13`) and the SHA-256 of every file. The public key is `basecamp/release_key.pub` (base64, committed); the private key is a PEM file, `%USERPROFILE%\.basecamp-signing\release.key`, made by `scripts/new-signing-key.ps1`. Signatures are checked with `cryptography` (a new dependency, vendored in the zip like the rest) | 2026-10-27 | A well-reviewed library rather than hand-written Ed25519. Signing the whole zip means nothing in it is read before the signature checks out |
| D-54 | A newer release is downloaded and checked as soon as it's found, not when Install is pressed: signature first, then unpack to `versions\<v>.tmp\` (entries that would land outside are refused), then the files must match the manifest exactly (nothing missing, extra or changed; `__pycache__` ignored), the manifest's launcher and Python must be this PC's, and the release's migrations must apply to a throwaway copy of the DB. Only then is it renamed to `versions\<v>\` and offered. Install itself only makes Basecamp exit | 2026-10-27 | Install is quick and can't fail half way. A release that would break the DB or need a reinstall is refused with a message before anything changes |
| D-55 | The pre-update DB copy is made last thing on the way out, after the DB is closed, with SQLite's backup API (`db-backups\before-<v>.db`, newest 5 kept). Then `pending.txt` is written and Basecamp exits with code 3. If the copy fails, `pending.txt` isn't written, Basecamp exits with 0 (the launcher starts the same version again) and the page says why | 2026-10-27 | The copy then holds everything the old version wrote, including the Install audit entry. No copy, no update: a rollback without it would pair old code with a newer DB |
| D-56 | Launcher protocol: it runs `python -s -m basecamp` in the version folder with `PYTHONPATH=<version>;<version>\lib` and `BASECAMP_ROOT`, `BASECAMP_DATA_DIR` and `BASECAMP_LAUNCHER` (its version number, for `min_launcher`) set. A swapped-in version is on trial (`trial.txt`, so a launcher restart in the middle still checks it) until `/healthz` answers with **that** version. If it exits or doesn't answer within 60 s, only Basecamp's own process is killed, `before-<v>.db` replaces the DB (its `-wal`/`-shm` removed), `current.txt` goes back to `previous.txt`, and `update-failed.json` says why. Exit 3 without a usable `pending.txt` restarts the same version. Crash back-off is 5 s doubling to 5 min, reset after 5 min up. Pruning keeps the newest 3 version folders plus current, previous and pending. `launcher.lock` stops a second launcher in the same folder | 2026-10-27 | The version check catches an old Basecamp still holding the port. Killing the process tree would take the game hosts with it wherever breakaway failed (R-93) |
| D-57 | Self-update state lives in `<data>\selfupdate.json`, not the DB. A version that rolled back is never auto-installed; Install by hand still works, after a confirm that says it failed before | 2026-10-27 | A rollback restores the DB, which mustn't make Basecamp forget the rollback. Auto-install retrying a broken version every night would roll back every night |
| D-58 | Settings: `update_repo` (`dwyer94/basecamp`), `update_api` (GitHub; https only, except to this PC so the dev PC can use `tools/fake_releases.py`), `update_check_h` (6; 0 = Check now only), `update_beta` and `update_auto_hour` (-1 = off). The ETag is kept per URL. Check, Install, Dismiss and refused installs are audited (`update.*`) | 2026-10-27 | R-90, R-94. The release source has to be swappable to test updates without publishing anything |
| D-59 | `release.ps1` needs a clean `main` equal to `origin/main`, a `CHANGES.md` section for the version, and passing tests and ruff. A version with a `-` is a pre-release. `build_release.py --test-key` (tests and the dev PC's end-to-end run only) ships the signing key's public key in the zip; without it the key must match the repo's | 2026-10-27 | The prod PC installs whatever the newest release is, so publishing is a deploy and gets its own confirmation. | D-60 | Under `python -m basecamp` without the launcher (dev runs), updates are still checked and staged in `<data>\updates\`, but Install is refused and the banner says why | 2026-10-27 | There's nothing to swap to; a clear message beats an exit that nobody restarts |
| D-61 | Stop warning (R-25) = an optional `stop_warning` per server: `{action: stdin or rcon, command, minutes}`, `{minutes}` and `{seconds}` replaced as plain text (other braces untouched), minutes sorted high to low, up to 6, each over 0 and at most 60; no minutes = off. Stored as a JSON column (migration 0005, default null). It runs inside the stop, restart or update with the server's lock held and only for a Running server: the first minutes value is the lead time, each value is a reminder. A warning that can't be sent ends the countdown and the stop goes ahead, as a stop step that can't be done is skipped (D-18). Templates give the command with no minutes, so the warning is off until the owner turns it on | 2026-10-27 | Holding the lock keeps a second stop, a start or a restore from slipping in during the countdown, with no new state in the state machine (the server is still Running, which is true). | D-62 | Who warns: the page's Stop and Restart (and **Restart now** after a config save), and updates. Not crash restarts, `stop_all`, or code calling `stop()` (the default is no warning). Cancelling an update during its warning leaves the server running with nothing changed | 2026-10-27 | Owner's brief: kill skips it, admins can stop now. A restart that came back after Kill would undo the admin's choice |
| D-63 | Live status message (R-63): off by default (`discord_live_status`, Settings page). First post: `POST <webhook>?wait=true` for the message id; then `PATCH <webhook>/messages/<id>`; a 404 means deleted, so post again. `<data>\live-status.json` keeps the id with a hash of the webhook URL (not the URL), so a new webhook gets a new message. Main webhook only | 2026-10-27 | Edits keep the channel from filling up with status; event messages still notify people. A per-server webhook (D-37) has no single place for a list of every server |
| D-64 | Backup download (R-54): `GET /api/servers/{id}/backups/{name}/download`, admin only.
